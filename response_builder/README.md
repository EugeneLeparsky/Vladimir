# Конструктор проектов откликов rabota.by

Работает только с откликами на существующие вакансии работодателя. Поиск резюме,
избранное, публикация вакансий, переписка и изменение статуса кандидатов не входят
в этот инструмент. Старые файлы `HR_Engine` и проекты не изменяются.

## Установка на Windows

1. Установите Python 3.12 с Windows Python Launcher (`py`).
2. Поместите **директорию `response_builder` целиком** и два файла
   `create_response_project.bat`, `install_response_builder.bat` непосредственно
   в `C:\HR UD\Конкурсы`. Не заменяйте существующие файлы с этими именами без проверки.
3. Запустите `install_response_builder.bat`. Он создаёт отдельное окружение
   `_shared\response_venv`, устанавливает зависимости и Chromium Playwright.
   Он не изменяет зависимости старых автоматизаций.
4. Запустите `create_response_project.bat`. Если Google credentials ещё нет,
   запускатор запросит ключ service account и OAuth client типа Desktop app.
   Выберите скачанные JSON-файлы в диалоге Windows или вставьте JSON одной строкой
   через скрытый ввод. При недоступном диалоге можно ввести путь к файлу.
   Запускатор проверит формат и сохранит credentials централизованно в `_shared`.
   При следующих запусках корректные сохранённые файлы используются без повторных
   запросов. Некорректный существующий файл заменяется только после явного «ДА»;
   ошибочный новый файл не повреждает старый. Содержимое JSON не печатается.
   `start_project.bat` также запросит service account, если общий файл отсутствует.
   Можно заранее подготовить эти общие файлы вручную:

   | Файл | Назначение |
   | --- | --- |
   | `google_service_account.json` | Service account для повседневной работы с Sheets. Поддерживается также имя `google_credentials.json` в этой же директории. |
   | `google_oauth_client.json` | OAuth client **Desktop app**, скачанный из Google Cloud. |
   | `rabota_auth.json` | Общий Playwright storage state; при отсутствии/истечении мастер открывает браузер для входа работодателя. |
   | `google_oauth_token.json` | Создаётся интерактивным OAuth-входом; вручную заполнять не нужно. |

В Google Cloud включите Google Drive API и Google Sheets API. Настройте OAuth
consent screen и разрешите своему аккаунту вход (для приложения в режиме Testing —
добавьте аккаунт в test users). Scope Drive нужен для поиска и копирования
существующего шаблона и предоставления доступа service account. Пользователь OAuth
должен видеть шаблон и иметь право его копировать/предоставлять доступ к копии.
Ограничения Google Workspace на external sharing могут блокировать выдачу доступа.

Credentials, tokens, cookies и `_shared` не следует добавлять в Git, архивы для
передачи или логи. Ограничьте доступ к `_shared` средствами Windows. Секреты не
копируются в проекты. SQLite и Google-таблица содержат персональные данные
кандидатов; доступ к ним также должен соответствовать вашим правилам хранения.

## Создание проекта

Запустите `create_response_project.bat` и задайте имя. Мастер:

1. Проверяет конфликты папки и имени таблицы. Можно выбрать другое имя или отменить.
2. Запрашивает ID/ссылку **«Тест ИИ»**, получает листы и предлагает выбрать лист
   и столбцы ФИО, возраста, телефона и ID резюме. Значения B/C/D/Z по умолчанию
   соответствуют существующему `core_parser.py`; их нужно сверить с вашим шаблоном.
3. Загружает вакансии из кабинета работодателя, показывает номера и позволяет
   выбрать несколько через запятую.
4. Проверяет реальную схему откликов, как описано ниже.
5. Копирует весь файл через **Drive `files.copy`**. Все исходные листы, значения,
   формулы, форматирование, ширины и фильтры копируются. Сам шаблон не изменяется.
6. Даёт общему service account право writer **на новую копию**, добавляет справа
   от существующих столбцов служебные поля в выбранном листе, создаёт проект и
   выполняет чтение Google и первичную проверку откликов.

Значения исходного шаблона в копии не очищаются. Сборщик использует свободные
подготовленные строки, не перезаписывая заполненные столбцы кандидата. При
необходимости расширяет копию и переносит формат/валидацию подготовленной строки.
Новые технические поля: ключ отклика, ID отклика, ID/название/URL вакансии, время
поступления, время сбора, email и доступный текст резюме. URL резюме находится в
кликабельном поле ФИО; ID резюме сохраняется отдельно.

В проекте появятся `project_config.json`, `collect_responses.py`,
`start_project.bat`, `state`, `logs`, `errors`. Код сборщика общий, а скрипт проекта
загружает его из соседней `response_builder`; сохраните эту директорию при переносе.
Вакансии берутся исключительно из `project_config.json`.

## Важная проверка схемы rabota.by

В исходном коде подтверждены `resumeId` и ссылка на резюме из
`negotiationLinks.changeTopic.defaultLink`, но **не подтверждены** поле ID отдельного
отклика, его дата и универсальный признак входящего обращения. Живой API в облачной
проверке был недоступен из-за HTTP 403 сетевого прокси.

Мастер не подставляет вымышленные имена полей. На Windows он предлагает выбрать
известный входящий отклик и выводит **только названия/типы полей**, без содержимого.
Имена и типы сохраняются в `_shared\response_schema_fields.json`.
Необходимо указать dot-path поля **устойчивого ID отдельного отклика**, поля времени
его поступления и признака входящего обращения/допустимые значения этого признака.
Если API содержит только входящие обращения, это требуется явно подтвердить.
Подтверждённая схема сохраняется в `_shared\response_schema.json` для следующих
проектов; каждый проект получает собственную копию схемы без секретов в конфиге.

**Если ID или смысл даты неизвестен, прервите мастер и исследуйте схему API.**
`resumeId`, `vacancyId`, страница, позиция, ФИО и дата обработки не заменяют ID
отклика. Наличие скалярного поля само по себе не доказывает его смысл — мастер
запрашивает явное подтверждение. Синтетические поля в тестах не описывают живой API.

Даты поддерживаются как ISO 8601 с часовым поясом, Unix seconds или milliseconds;
в таблицу попадает время поступления в UTC. Время без часового пояса не угадывается.
Не используйте время последнего сообщения вместо времени поступления отклика.
Не выбирайте `hasNewMessages` в качестве признака входящего отклика: прочитанные
отклики тоже должны собираться. При настройке статусного признака учитывайте уже
обработанные/перемещённые входящие отклики, а не только текущий статус `RESPONSE`.

Без подтверждённой схемы/образца мастер не создаёт таблицу и не заявляет готовность.
При изменении сайта сохранённая схема может потребовать повторного исследования.

## Запуск проекта

`start_project.bat` содержит:

1. TEST — максимум **одна попытка записи нового отклика**, видимый браузер.
2. FULL — новые отклики, headless.
3. Проверка Google + rabota.by и ручное восстановление сессии при необходимости.
4. Повтор ошибок из локальной очереди, видимый браузер.
5. FULL — видимый браузер.
6. Выход.

При отсутствующей/истёкшей сессии даже headless-запуск открывает видимый браузер
для ручного входа, после чего возвращается к headless. Нужен интерактивный рабочий
стол; для полностью unattended-запуска заранее выполните пункт 3.
Проверка не пишет кандидатов в таблицу и не меняет статусы/сообщения.
Открытие резюме для сбора может отметить его просмотренным на самом сайте.
Отсутствующий закрытый телефон/email допустим, ошибка открытия резюме — причина
поместить запись в очередь ошибок. Снимки страницы и сырые HTTP-ответы не логируются.

Коды завершения CLI: 0 — операция завершена без выявленных ошибок; 1 — ошибка или
неполный проход; 2 — TEST не нашёл нового отклика, запись не проверена.
BAT показывает код и возвращает пользователя в меню.

## Дедупликация и возобновление

Ключ — JSON-пара `[vacancy_id, response_id]`. Разные вакансии и повторные отдельные
отклики одного резюме имеют разные ключи. Конфликт одного ключа с другой датой/резюме
фиксируется как ошибка, а не поглощается дедупликацией.

SQLite `state\responses.sqlite3` хранит очередь, payload, закреплённую строку,
состояние и число попыток. Строка и payload фиксируются **до** записи Google.
Данные и ключ записываются одним атомарным `spreadsheets.batchUpdate`, затем ключ
проверяется чтением и фиксируется checkpoint. Если сервер записал данные, но ответ
потерялся, следующий запуск сверяет ключи таблицы и не отправляет дубль.
При остановке между резервированием и записью продолжается та же строка.
Одновременные процессы одного проекта запрещены OS-lock.

Занятую закреплённую строку, дубли ключей и исчезнувший ранее сохранённый ключ
сборщик не исправляет перезаписью: нужна ручная проверка. Не удаляйте служебные
столбцы; сортируйте только **весь диапазон вместе с техническими столбцами**.
Не запускайте ручную сортировку/редактирование строк одновременно со сборщиком.
Состояние и таблица должны резервироваться вместе. Сортировка незавершённых строк
может потребовать ручного восстановления очереди.

`errors\records.jsonl` — ошибки записей с известным устойчивым ключом;
пункт 4 повторяет именно эту очередь. `errors\discovery.jsonl` — ошибки обхода/
схемы, где устойчивый ключ может отсутствовать. После исправления схемы/сети для
них нужен новый FULL, а не выдуманный ключ. Успешно поставленные в очередь записи
обрабатываются и после частичной ошибки обхода, но проход возвращает код 1.
`logs\last_run.json` содержит итог последнего завершившегося прохода.

## Незавершённое создание

При ошибке проект остаётся `creation_failed`/`creating`; его launcher не позволит
сбор. ID уже созданной копии сохраняется в конфиге до последующих операций.
Возобновление только для папок этого мастера:

```bat
create_response_project.bat --resume "Название проекта"
```

Попытка копирования отмечается до запроса и получает уникальный `appProperties`
маркер. После неопределённого ответа мастер ищет копию по этому маркеру и не
повторяет запрос автоматически. Если копия ещё не видна, повторите возобновление
позже. Только после ручной проверки отсутствия копии можно вызвать:

```bat
create_response_project.bat --resume "Название проекта" --retry-copy
```

Потребуется явно ввести имя проекта. Существующая одноимённая таблица всё равно
блокирует новую копию. Частичные копии не удаляются автоматически. Изменённые
пользователем скрипты/launchers при возобновлении не перезаписываются.

## Проверка разработки

Из корня репозитория/установки:

```bat
py -3.12 -m unittest discover -s response_builder/tests -v
```

Тесты используют искусственный API и не обращаются к реальным кандидатам или
таблицам. Они проверяют запись, дедупликацию между вакансиями, повторные отклики,
checkpoint, потерянный ответ Google, повтор ошибок и защиту существующих данных.
Перед эксплуатацией отдельно проверьте настоящий шаблон/схему и выполните TEST
на Windows. BAT и интерактивный OAuth не проверялись запуском в Linux.

Для Linux-разработки укажите `--root /абсолютный/путь` явно. При необходимости
системный Chromium можно задать `RESPONSES_BROWSER_EXECUTABLE=/usr/bin/chromium`;
по умолчанию используется браузер, установленный `playwright install chromium`.
Никакие TLS/checksum проверки не отключаются.

Сетевые направления: `rabota.by` и его используемые поддомены,
`accounts.google.com`, `oauth2.googleapis.com`, `www.googleapis.com`,
`sheets.googleapis.com`, а для установки — PyPI и CDN Playwright. В облачной
среде они должны быть разрешены настройками; установка VPN/обход сетевой политики
не выполняется.
